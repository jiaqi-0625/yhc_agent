> 交接基准日：2026-08-19  
> 目标分支：`main`  
> 产品范围：汽车信息流广告资产生产，不包含广告发布和媒体投放  
> 产品与实施权威规格：[`workspace-v2-product-spec.md`](./workspace-v2-product-spec.md)

## 1. 项目现状摘要

项目正在从现有“车型快照 → 营销策略 → 人工审批”的本地纵向切片，迁移到 Workspace V2 的完整领域层级和六阶段制作工作流。

Workspace V2 的业务层级是：

```text
tenant → brand → vehicle → batch project → video task
```

视频任务的权威流程是：

```text
strategy → asset matching → script → storyboard → video preview → delivery
```

截至交接基准日：

- 工作区线已完成共享 Schema、模块拆分、六阶段状态机、逐阶段人工确认和不可变版本落盘，完成到 `WS-102`。
- 对话区线已完成任务上下文/操作卡片契约适配、Agent 模块拆分适配，以及 `AG-207` 的非技术用户友好展示；部分能力仍是旧 `workId` 兼容链路或 Mock 垂直切片。
- 全仓最近一次记录的检查结果为 `npm run check` 通过，共 76 项测试。
- 当前没有阻止本地 Mock 垂直切片继续运行的阻塞；完整权限、账号隔离、预算和统一命令闭环仍依赖后续工作区任务。
- 交接时必须用 `git status --short --branch` 和两份实时台账再次确认远端集成状态；台账只在提交进入 `origin/main` 后把任务标为“已完成”。

## 2. 负责板块与代码所有权

### 2.1 工作区负责人

主要负责业务领域、服务端权威状态和工作区 UI：

| 范围 | 主要职责 | 主要路径 |
|---|---|---|
| 共享契约 | 品牌、车型、项目、任务、资产、版本、命令契约 | `packages/schemas` |
| 领域规则 | 工作流、权限、revision、负责人、并发锁、预算、回退失效 | `packages/domain` |
| 领域端口 | 公司资产、视频生成、自动剪辑端口及 Mock 适配器 | `packages/tools` |
| 工作区 API | 管理中心、项目、任务、资产及统一命令 API | `apps/api` |
| 工作区前端 | 应用壳、项目库、创建向导、中间工作区 | `apps/web` |

共享 Schema 和领域转换由工作区负责人维护最终结构。对话区需要新增字段或命令时，应先提出契约变更，不建立平行类型，也不绕过领域层。

### 2.2 对话区负责人

主要负责任务级 Agent、会话和右侧面板：

| 范围 | 主要职责 | 主要路径 |
|---|---|---|
| Agent 运行时 | 装配、系统行为、会话、流式事件、工具白名单 | `packages/agent` |
| Agent API | 会话创建/恢复/取消、消息和 SSE | `apps/api/src/agent-routes.ts` 等 Agent 模块 |
| Agent 前端 | 右侧面板、时间线、上下文条、操作卡片 | `apps/web/public/agent-*` |
| 安全与质量 | 会话隔离、脱敏、审计、工具边界测试 | `packages/agent/test`、相关 API/Web 测试 |

Agent 只能提出领域操作卡片。状态变更、人工确认和高消耗操作必须由用户显式触发，并由后端重新校验权限、状态、revision、预算和幂等性。

### 2.3 需要共同评审的共享热点

- `packages/schemas/src/index.ts`：共享契约的最终结构。
- `packages/domain`：业务状态和领域转换。
- `apps/api/src/server.ts`：仅作为组合入口，新增逻辑优先进入拆出的路由/服务模块。
- `apps/web/public/app.js`、`index.html` 和全局样式：仍可能影响工作区与 Agent 两条线。
- `AGENTS.md`、产品规格和两份实时台账：业务边界或协作规则变化时必须同步更新。

## 4. 关键业务与安全约束

以下约束不能靠提示词保证，必须由 Schema、领域层、API 和测试共同执行：

1. 对话历史不是业务状态源；权威状态来自服务端工作流聚合。
2. 身份、租户、品牌、项目、任务和负责人范围只从认证会话解析，不能接受模型或客户端声明。
3. 车型事实只来自版本化车型快照；模型输出不能成为官方事实。
4. 人工编辑和锁定字段优先于模型输出；模型不能批准自己的工作。
5. 每阶段确认都生成不可变版本；回退必须使依赖的下游产物失效。
6. 一个账号同一时间最多运行一个高消耗视频任务；不同账号可以分别运行。
7. 每个视频任务同一时间只有一个活动负责人；接管和旧 revision 冲突必须由后端处理。
8. 公司资产只读且 Provider 可替换；车型资产不能跨车型替换，人物和场景可以从公司目录替换。
9. 任务开始策略工作时锁定车型和资产快照；项目资产池继续跟踪最新目录。
10. 平台选择只是视频任务元数据标签，不改变生成规则。
11. 生产 Agent 只注册领域专用白名单工具，不得暴露 shell、文件系统、SQL、任意 HTTP、浏览器或人工批准工具。
12. 自动化测试只使用 Mock Provider，不得产生真实模型或视频生成费用。

## 6. 本地启动与验证

环境要求：Node.js 22.19 或更新版本、npm 10 或更新版本。

```powershell
npm install --ignore-scripts
npm run check
```

`npm run check` 依次执行严格 TypeScript 检查、自动化测试和凭据模式扫描。生产依赖审计可另行运行：

```powershell
npm run audit:prod
```

无真实模型费用的本地 API/UI 验收，建议在本地 `.env` 中使用 Mock Provider，然后启动：

```powershell
npm run dev:api
```

默认访问 `http://127.0.0.1:3100/`。如果 3100 端口已有旧进程，先确认进程和健康检查，不要误把旧静态资源 404 当成当前代码问题。任何真实模型联调都必须显式确认 Provider、密钥来源和费用风险；不要在日志、fixture、文档或提交中记录密钥。

## 7. 已知风险、依赖和待决事项

- 远端集成状态：交接前后都要检查 `main...origin/main`，不能仅凭本地提交或台账备注宣称已完成。
- V1/V2 双路径：旧 `workId`、`WorkStatus` 和作品端点仍用于兼容切片，迁移期间最容易产生状态源混用。
- 权限闭环未完成：跨租户、跨品牌、负责人、接管、额度和高消耗任务锁尚未全部实现。
- 操作卡片仍有兼容端点：在 `WS-305` 之前，不能宣称统一命令的权限、预算和幂等闭环完成。
- 本地 JSON 仅是开发适配器：数据库、队列、对象存储和生产部署方案仍在待确认列表中。
- README 和架构说明主要描述早期策略纵切，后续应在 `WS-505/AG-507` 统一更新，当前以产品规格和实时台账为准。
- 模型、数据库、队列、对象存储、部署平台和车型数据源仍需业务/基础设施确认，详见 `docs/decisions/open-decisions.md`。

## 8. 建议的接手顺序

1. 同步并确认 `main`：`git fetch origin`，检查本地与 `origin/main` 的 ahead/behind 数量和工作区状态。
2. 阅读产品规格的领域层级、六阶段流程、Agent 边界和 12 条验收标准。
3. 阅读两份实时台账及最近任务备注，以提交哈希和测试记录核对真实完成状态。
4. 运行 `npm run check`，再用 Mock Provider 完成一次桌面浏览器验收。
5. 工作区优先领取 `WS-103`；对话区优先完成不依赖未落地服务端能力的评审/整理工作，并避免提前宣称账号隔离或统一命令闭环完成。
6. 每次开始、推送、阻塞或评审转换后立即更新对应台账；共享契约或业务边界变化时同时更新两条线和产品/决策文档。
